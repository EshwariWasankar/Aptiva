1. Project overview
Item
Content
Name
Aptiva
 [C] (renamed from PrepPilot)
Context
A Web Technologies course project that is also designed as a product. Placement hiring in India is gated by online aptitude assessments; the first round eliminates most candidates.
Problem
Students have abundant practice material but no way to decide how to spend limited time. They lack: an assessment-specific target level, the cause of lost marks, visibility of speed, a plan that fits days (not weeks), and a view of how current a test pattern is.
Solution
A planning layer above question banks. It combines the student's measured ability (accuracy, speed, error causes), the target assessment's blueprint, and the time available, then produces a time-boxed daily plan that is recomputed after every session.
Users
Final-year engineering students (primary); pre-final-year students; off-campus aspirants; internal content admins and reviewers.
Core objectives
(1) Per-topic Readiness Gap with sources and confidence. (2) Time-boxed plan maximising expected gain per minute. (3) Error-cause and speed diagnosis. (4) Adaptive re-planning. (5) Pilot-measured impact.
Differentiator
The combination of assessment-specific target, time-boxed optimisation, error-cause diagnosis and speed readiness. Not the size of the question bank.
Role of ML
Classical statistical estimation and rules (Elo/Glicko-2 with uncertainty, EMA, rule-based error inference, priority scoring, knapsack planning). 
No trained model is needed for the MVP.
 Estimation is essential to the core product, but it is not a learned model. Python batch jobs (duplicate detection, item statistics) are optional enhancements.
Deliverables
Student web app (responsive, PWA-ready), admin console, a reviewed question bank (target 400–600 items), 8–10 assessment blueprints with provenance, deployed system with CI/CD, documentation set, pilot evaluation.
Problem, solution and implemented functionality are different things.
 Pricing, community and coding modules appear in the product vision but are outside the MVP (Section 2).

4.2 Sequence: answer submission (highest-risk flow)
sequenceDiagram
  participant B as Browser
  participant A as NestJS API
  participant R as Redis Stream
  participant W as Consumer worker
  participant D as PostgreSQL
  B->>A: PUT answer (attempt id, input)
  A->>A: stamp server time, mark from cached key
  A->>R: XADD attempt event, update session aggregates
  A-->>B: correctness, expected time, feedback
  W->>R: read batch (max 100 or 1 s)
  W->>D: INSERT ... ON CONFLICT DO NOTHING
  W->>R: ack
  B->>A: POST finish session
  A->>A: flush barrier (reconcile ids, drain stream)
  A-->>B: 202 recalculation pending
4.3 Edge cases (all workflows)
Assessment missing from the catalogue; fewer than 24 hours left (skip deep diagnostic, show a 20–30 minute plan and an honest message); missed days (compress, no guilt wording); test date moved or new target added; thin data; abandoned diagnostic; duplicate submission of the same attempt id (return stored result); cancelled session (partial attempts kept, no recalculation until the student finishes or the session expires after a stated timeout [P] of 2 hours).

5.3 Request lifecycle
Browser request → CDN or host edge → NestJS guard chain (rate limit, JWT, role, object ownership) → validation (zod or class-validator) → controller → service → engine (pure functions) → Prisma → response envelope. Answer submissions diverge: they mark from cache, append to the Redis stream and return before the database write (Section 11, E-041).

11.5 Asynchronous processing
Submitting finish (E-042) or diagnostic submit (E-014) returns 202. A BullMQ job runs the flush barrier then recalculation. Status is read from E-043 or E-031 (
recalcStatus
). Failed jobs retry up to 3 times with exponential backoff (safe because recalculation is a pure function of persisted attempts and is idempotent by session id). After final failure the status is 
failed
, an alert is raised, and the student sees a neutral banner with a retry action.

Engine:
 PostgreSQL [C]. Relational integrity is needed across attempts, profiles, blueprints and plans. 12.4 Design notes
Normalisation:
 third normal form for content and identity; JSONB only for derived or semi-structured data (rationale, error mix, summaries, per-weekday minutes).
Transactions:
 the consumer batch insert runs in one transaction; recalculation updates 
student_topic_profiles
, inserts a snapshot, then the plan, in one transaction per user.
Concurrency:
 recalculation takes a per-user advisory lock; 
practice_sessions.recalc_status
 changes by compare-and-set so a retried job cannot run twice; attempts are protected by the primary key.
Ownership and access:
 every student table has 
user_id
; the ORM layer exposes only owner-filtered repository methods for student routes.
Retention
 (to confirm with counsel): attempts, error reports and readiness history for the active period plus 12 months; security records 12 months; uploaded documents deleted after extraction or within 30 days.
Growth:
 partition 
question_attempts
 by month when volume warrants it [P, P2].

Principles.
 Collect only what personalisation and operation need: no phone number, date of birth or government id. Behavioural data is sensitive: it is never shown to other students, never sold or shared with employers, advertisers or colleges, and never used for employability scoring or hiring. 42. Glossary
Term
Meaning
Readiness Gap
Difference between the student's estimated level at pace and the internal planning target band for a topic
Baseline profile
The first skill, performance and error estimate, built from the setup diagnostic and shown as an early estimate
Blueprint
Structured description of an assessment (sections, durations, counts, negative marking, topic shares) with a source type and confidence per field
Provenance
The source type of a blueprint field: official, public, candidate-reported, pattern-inferred or assumption
Pool
A disjoint set of questions reserved for diagnostic, practice or reassessment
Cell
One topic and difficulty combination used to measure bank depth
Rationale
JSON stored on each plan item holding the exact factors behind it; rendered as Why this?
Engine
The pure TypeScript library that does marking, rating, error inference, priority, planning and readiness
RD
Rating deviation, the uncertainty of a rating
EMA
Exponential moving average
Pace ratio
Student's average time divided by the blueprint's expected time for the topic
Flush barrier
The step at session end that waits until all buffered attempts are persisted before recalculation
Probe block
A short practice block that gathers evidence for a thin-evidence topic
Maintenance block
A small review that keeps a strong topic from decaying
Cram mode
Final 48 hours: high-yield review and speed drills, no new heavy topics
Planner fallback
The deterministic priority-ranked plan used when the knapsack exceeds its 250 ms budget
